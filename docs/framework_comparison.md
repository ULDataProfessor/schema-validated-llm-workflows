# Framework Comparison Matrix

Comparison of PydanticAI, LangGraph, DSPy, CrewAI, Agno, and a plain SDK baseline for business analytics agent workflows. Ratings are qualitative (1 to 5) based on framework design, documentation, and the current benchmark implementation. They are not empirical performance results.

## Current Artifact Status

All six framework conditions now have runner implementations for the five benchmark tasks. The DSPy runner is an untuned typed-signature baseline; optimizer experiments remain a separate planned condition. The CrewAI runner is a single-agent structured-output baseline; multi-agent CrewAI workflows remain planned ablations. The local smoke tests exercise dry-run behavior and missing-package failures without making API calls.

## Feature Detail

### PydanticAI

- **Strengths:** `output_type` with Tool/Native/Prompted modes; `@agent.output_validator`; dependency injection (`deps_type`); TestModel for unit tests; streaming structured output (beta).
- **Weaknesses:** API churn; native structured output incompatible with tools on some models (e.g., Gemini); multi-agent less opinionated than CrewAI.
- **Business fit:** Invoice extraction, API-facing agents, strict audit schemas.

### LangGraph

- **Strengths:** Explicit state graph; checkpointing; human-in-the-loop; conditional edges; strong debugging via LangSmith.
- **Weaknesses:** Higher boilerplate; structured output depends on LangChain stack; steeper onboarding.
- **Business fit:** Approval workflows, multi-step analytics pipelines with rollback.

### DSPy

- **Strengths:** Compile-time optimization (BootstrapFewShot, MIPRO); separates program from prompts; strong on NL2SQL with tuning.
- **Weaknesses:** Optimization cost; different mental model; less suited to one-off schema contracts.
- **Business fit:** SQL generation, repeatable pipelines with labeled dev sets.

### CrewAI

- **Strengths:** Fastest path to multi-agent; role/goal/backstory abstraction; large ecosystem.
- **Weaknesses:** Weaker compile-time types; debugging non-linear flows; validation not first-class.
- **Business fit:** Research + report drafting, marketing analytics prototypes.

### Agno

- **Strengths:** Lightweight; Pydantic-native; fast agent definition; good tool support.
- **Weaknesses:** Smaller community; fewer production case studies; documentation evolving.
- **Business fit:** Single-agent extraction and Q&A with typed outputs.

## Comparison Against Plain SDK

| Capability | Plain OpenAI/Anthropic SDK | PydanticAI |
|------------|---------------------------|------------|
| Schema enforcement | `response_format` / tools | Same + validation + retries |
| Agent loop | Manual | Built-in |
| Tool registration | Manual JSON schema | `@agent.tool` + types |
| Testing | Mock API | TestModel + DI |
| Observability | Manual | OTel hooks |

Plain SDK is the **lower bound** for abstraction and the **baseline** for latency/token overhead introduced by frameworks. It is not a straw man: provider-native structured output may be sufficient for narrow single-call workflows.

## Empirical Questions per Framework

| Framework | What we might find |
|-----------|-------------------|
| PydanticAI | Strong schema validity and low implementation size when typed outputs dominate |
| LangGraph | Strong traceability and workflow control, with higher code overhead |
| DSPy | Competitive SQL or summarization after optimization, with tuning cost |
| CrewAI | Fast role/task modeling, but less type-safety emphasis in the primary abstraction |
| Agno | Near PydanticAI on simple typed-output tasks if provider structured output dominates |
| Plain SDK | Competitive on narrow single-call tasks, weaker on retries, tools, and trace structure |

*Fair comparison requires identical prompts, temperatures, and model versions; see benchmark protocol.*
